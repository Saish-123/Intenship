For Week 3 I took my responsive Ridgeline Trail Club page from Week 2 and made it genuinely interactive using only plain JavaScript, with no libraries or frameworks. Before coding I reviewed each element of the static page and asked what a visitor is trying to do: find a suitable hike, check whether there is space, and book it. That led to eleven features, led by a trail filter with live search and sorting, a schedule whose dates are recalculated from today's date, and a booking form with proper validation. Booking a hike also updates the seats remaining in the schedule immediately. Supporting features include an accessible mobile menu, a photo lightbox built on the native dialog element, a dark mode that remembers the visitor's choice, scroll-spy navigation, a back-to-top button and scroll animations that respect reduced-motion settings.

The code is organised as independent feature functions, each wrapped in error handling, which communicate through custom events rather than shared variables. JavaScript changes state such as aria-expanded and classes, while CSS controls how that state looks. The page uses progressive enhancement, so it remains fully usable with JavaScript switched off, and it causes no layout shift when scripts load.

The technical document explains the plan, structure, each feature and the decisions behind it, with code excerpts and screenshots. It also records the testing evidence: 74 automated browser checks all pass, axe-core reports zero accessibility violations in light and dark themes, and HTML, CSS and JavaScript linters report no errors. The debugging log lists the real bugs the tests caught and how I fixed them. I tested in Chromium only, not on physical devices, and bookings are simulated in the browser. The report ends with specific next steps, such as sending bookings to a server and sharing filter state in the address bar.
